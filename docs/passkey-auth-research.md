# Passkey authentication research

Checked 2026-10-01 against official documentation, upstream source, and installed `@convex-dev/auth` **0.0.96**. Research only: no application or production changes.

Implementation followed this research. See [configuration, validation, and cutover instructions](./passkey-auth-operations.md) for the implemented behavior and current rollout status. Optional user-chosen passkey syncing was explicitly accepted; EloMondo uses no external login provider.

## Recommendation

Keep Convex Auth for sessions and add a custom `ConvexCredentials` passkey provider using SimpleWebAuthn for the WebAuthn ceremonies. This avoids an identity service, email delivery, OAuth, and replacing the app's existing user IDs. Convex Auth's documented built-in methods do not include passkeys; this is an application-owned integration, not a configuration switch. [Convex Auth](https://labs.convex.dev/auth)

Passkeys use a public key on our server and a private key in the user's authenticator. Synced passkeys can use Apple/Google/password-manager infrastructure chosen by the user, but our app does not authenticate against those services. Device-bound authenticators/security keys are an alternative when the user also wants to avoid cloud synchronization. [WebAuthn specification](https://www.w3.org/TR/webauthn-3/), [SimpleWebAuthn passkeys](https://simplewebauthn.dev/docs/advanced/passkeys)

## Convex integration facts

- Installed `ConvexCredentials.authorize` accepts arbitrary client parameters and returns `{ userId, sessionId? }` or `null`. The existing sign-in implementation calls the normal session/token machinery after this return. A verified credential can therefore map directly to an existing `users._id`; no email matching or `authAccounts` entry is needed for this provider. [Provider source](https://github.com/get-convex/convex-auth/blob/main/src/providers/ConvexCredentials.ts), [Sign-in source](https://github.com/get-convex/convex-auth/blob/main/src/server/implementation/signIn.ts)
- `createAccount` has no explicit target-user-ID option. It offers verified email/phone linking; `createOrUpdateUser` can override linking, but is unnecessary for the direct-ID approach. Never enable email linking on the basis of a supplied legacy email. [Server API](https://labs.convex.dev/auth/api_reference/server), [Account linking](https://labs.convex.dev/auth/advanced)
- Direct authorization does not call the app's `afterUserCreatedOrUpdated` callback. New-user registration must explicitly create the player using the same business-ID convention; legacy registration must reuse the existing user and player. The app already stores `users.legacyId` and uses it for historical player ownership. [Current auth](../convex/auth.ts), [Schema](../convex/schema.ts)
- Current SimpleWebAuthn documentation describes **14.0.x**, requiring Node **22+**. Convex supports configurable Node 22/24 actions and defaults to Node 20. Put verification in an internal `"use node"` action called by the credentials provider; use internal queries/mutations for storage. Do not place `"use node"` on `auth.ts`, which exports a mutation/query too. Pin mutually compatible package versions when implementing. [SimpleWebAuthn server](https://simplewebauthn.dev/docs/packages/server), [Convex runtimes](https://docs.convex.dev/functions/runtimes)

## Proposed ceremony and storage

The following is engineering design based on the APIs above:

1. The server generates a random expiring challenge and stores its purpose, intended account, authorization evidence, origin/RP ID, consumption state, and a hash of a secret browser nonce. Require that nonce at completion to prevent ceremony substitution. Registration authorization comes from a recent passkey proof, an existing authenticated migration session, a user-specific claim token, or a recovery token.
2. The browser runs SimpleWebAuthn registration/authentication. Require discoverable credentials for account-picker login and require local user verification. Support both platform authenticators and security keys; store public key, credential ID, user handle, counter, transports, and backup/device metadata. The verifier checks the stored challenge, exact origin, RP ID, and user-verification flags. [SimpleWebAuthn server](https://simplewebauthn.dev/docs/packages/server)
3. After cryptographic verification, an internal mutation rechecks authorization, expiry, account eligibility, credential uniqueness, and the counter/challenge state. Atomically insert/update the credential, consume the challenge and claim/recovery grant, and mark the migration complete. Replays or competing claims must fail. The action returns that mutation's authoritative user ID to `authorize`, which creates the normal session. Never trust a client-selected user ID or a client `verified` flag.
4. Recovery grants authorize only registering a replacement passkey, not a general application session before registration. Offer multiple passkeys and offline one-time recovery codes, stored as hashes. Consuming a recovery code and registering the credential happens in the same transaction; revoke other sessions after recovery. Require recent passkey proof for credential removal and recovery-code regeneration.

Use **`elo.janjaap.de` as RP ID**, verify **`https://elo.janjaap.de`**, and redirect `elo.apps.janjaap.de` to the canonical host before ceremonies. The broader `janjaap.de` RP ID would widen browser credential scope to sibling subdomains; server verification still requires an exact origin allowlist. RP IDs are domain-bound; changing to a different RP ID generally requires credential enrollment again. HTTPS is required in production; localhost is supported for development. [WebAuthn specification](https://www.w3.org/TR/webauthn-3/), [SimpleWebAuthn server](https://simplewebauthn.dev/docs/packages/server)

## Legacy claiming

**A global claim password proves membership in the group that knows it, not ownership of the selected account.** Any holder could take another eligible user first. Making it server-only or rate-limited does not fix that identity problem. Recommended design: randomly generated, expiring, single-use **per-user claim codes**, handed to each person directly by the owner; no email needed. Issue codes through internal administration or an authenticated owner flow that requires recent authentication.

Eligibility needs an explicit migration state and owner-reviewed allowlist. **No passkey does not mean unclaimed.** The completed migration already allowed resets/sessions, and the imported admin has a password. Exclude disabled users, previously claimed accounts, active password accounts, and accounts with active recovery/session authorization unless an authenticated owner explicitly approves their migration. Preserve `users._id`, `legacyId`, player IDs, memberships, and history. [Cutover evidence](./convex-migration-handover.md), [Importer](../convex/migration.ts)

If shared-secret self-claiming is deliberately chosen for a trusted small group, acknowledge the takeover tradeoff. Keep a high-entropy secret in backend environment configuration, use a short deadline, an explicit allowlist, rate limits and audit records, and disable the endpoint permanently after migration. Do not hardcode the secret in source or the frontend bundle.

## Concrete product and implementation plan

This is the recommended implementation scope, not a change already deployed:

- **Create account:** enter a display name, create a passkey, and save offline recovery codes. Use an opaque stable user handle; email is unnecessary. Only create the user/player after successful registration. A name collision must never link to an existing account.
- **Sign in:** press “Sign in with passkey” and use the browser's account picker. No email or username prompt is needed for discoverable credentials. [SimpleWebAuthn passkeys](https://simplewebauthn.dev/docs/advanced/passkeys)
- **Migrate an existing account:** give the player an account-specific claim code after checking their identity directly. Enter the code, confirm the player name, and create a passkey. The code identifies exactly one account, so no public directory of claimable users or emails is needed. Existing authenticated users can enroll on their own account with recent authentication. A successful registration atomically disables all outstanding claim codes for that account; cancelled registration leaves it claimable.
- **Recover access:** prefer another enrolled passkey/security key. Otherwise enter a high-entropy, one-time offline recovery code and register a replacement passkey before receiving application access. Recovery codes are bearer secrets and are less phishing-resistant than passkeys. If every key and recovery code is lost, recovery needs a deliberate owner identity check; knowing a display name is insufficient.
- **Manage credentials:** list, label, add and revoke passkeys; require recent passkey proof for sensitive changes. Prevent removing the last passkey without a verified replacement. Offer a second independent key, especially for the admin.
- **Invite players:** keep the existing shareable group invite code/link and remove the email-invitation form and mutation. Invite codes grant group membership, never ownership of a legacy account. [Current invite flows](../convex/data.ts), [Group settings](../src/pages/GroupSettings.tsx)

Add credential, challenge, claim-grant and recovery-code tables, plus explicit migration eligibility/completion fields. Generate claim/recovery secrets with a cryptographic random generator (for example, 32 random bytes); store hashes, target user IDs, expiry, revocation and consumption metadata. Apply application-owned rate limits to registration, claim and recovery attempts, including through `auth.signIn`; do not assume the password provider's limits cover custom authentication. Never log claim/recovery secrets or expose private credential tables to public queries.

Replace the password/email flows in `convex/auth.ts`, `src/pages/Auth.tsx` and `src/contexts/AuthContext.tsx`; retain the existing Convex Auth React/session integration. Centralize user/player initialization so new passkey accounts get the same profile guarantees as today's callback. After migration, remove the Password/Email providers and mail configuration. Explicitly invalidate existing sessions and outstanding email verification/reset grants during cutover; removing the password provider alone does not revoke existing sessions.

Email can remain optional in the auth library schema for compatibility, but migrated values and email-addressed `authAccounts`/invitation data should be purged from the live database after claim issuance no longer depends on them. Old private backups retain their original contents unless separately removed. The existing importer/reset-only tests must be updated for the new migration contract; preserve the historical user/player IDs and business-table values.

Implementation order: first prove passkey verification and existing-user session creation in development; then add claiming, recovery and credential management; then audit eligible accounts and issue individual codes; finally remove email/password paths in one coordinated backend/frontend cutover. Verify invalid signatures, wrong origin/RP ID, expired/replayed challenges, concurrent claims, disabled/activated-account rejection, recovery replay, and preservation of legacy roles/history. Test actual devices as well as a virtual authenticator. No production account list or secrets were accessed for this research.

## Alternative and remaining checks

Better Auth now documents passkey-first registration with `requireSession: false`, a server `resolveUser` callback, and post-verification session creation. Its passkey plugin uses SimpleWebAuthn. However, passkeys are absent from Convex Better Auth's supported-plugin list and require custom schema/local installation; switching also changes sessions and user storage. It is a possible larger migration, not the least-change route here. [Better Auth passkeys](https://better-auth.com/docs/plugins/passkey), [Convex supported plugins](https://labs.convex.dev/better-auth/supported-plugins), [Vite integration](https://labs.convex.dev/better-auth/framework-guides/react)

Before implementation completion, verify the pinned verifier against the deployed Node runtime, challenge/counter races, current account eligibility, canonical-domain redirects, real Safari/iOS and Chrome/Android ceremonies, extra-key enrollment, recovery, and credential revocation. Cryptographic feasibility is established; no deployed end-to-end passkey implementation has been tested by this research.
